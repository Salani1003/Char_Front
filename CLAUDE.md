## Architecture

This is a React 19 + TypeScript + Vite app for "Char", split into feature domains under `src/`:

- `src/admin/` — admin screens (`layouts/CharAdminLayout.tsx`, `pages/<feature>/<Feature>Page.tsx`)
- `src/auth/` — auth screens (`layouts/AuthLayout.tsx`, `pages/login/LoginPage.tsx`)
- `src/components/ui/` — shadcn/base-ui primitives (button, input, label, card, ...). Screens must not import from here directly — see Component architecture below.
- `src/components/char/` — Char's own Design System components (own API/variants/identity), wrapping `components/ui` primitives. Screens import from here.
- `src/components/forms/` — react-hook-form integration layer (`FormInput`, `FormPasswordInput`, `FormTextarea`, `FormSwitch`, `FormCheckboxGroup`, `FormSelect`, `FormCombobox`), built on top of `components/char`.
- `src/styles/tokens.css` — Char design tokens (color, radius, spacing, typography, elevation, motion), imported by `src/index.css` and bridged into Tailwind utilities via `@theme inline`.
- `src/lib/` — shared utilities (`cn()` helper combining `clsx` + `tailwind-merge`; `apiError.ts` normalizes DRF errors — including nested ones, flattened to dotted keys — into `ApiError` (a body that is a plain list of strings becomes `message`; a duplicate-name 400 with `existing: {id, name}` is exposed as `ApiError.existing` with a numeric `id` and removed from `fieldErrors`), and `applyApiErrors.ts` maps them onto a react-hook-form)
- `src/hooks/` — shared hooks (`useDebounce`, `useDocumentTitle` to set the tab title per screen)
- `src/references/` — a reference Char UI kit (design tokens, atoms/molecules/organisms/templates as `.jsx` + `.prompt.md`) used as the source of truth for the brand's visual identity. Not wired into the app — consult it when porting a new component into `components/char`, don't import from it directly.
- `src/design-system/` — the `/design-system` route: a live, interactive catalog of every token in `tokens.css`/`index.css` and every `components/char` component. Reads token values at runtime via `getComputedStyle` (`src/design-system/lib/cssTokens.ts`) instead of duplicating them — when adding a new token or a new `components/char` component, add it here too so the catalog stays complete.

New feature pages should follow the existing `pages/<feature>/<Feature>Page.tsx` convention, and shared cross-page UI belongs in a layout under the relevant domain's `layouts/` folder.

### Component architecture

Char follows a layered component architecture (loosely Atomic Design, no strict enforcement):

```
components/ui (shadcn/base-ui primitive)
  → components/char (Char's own component: API, variants, identity)
    → components/forms (react-hook-form integration, when the component is used in a form)
      → screen
```

- Never import from `components/ui` in a screen — import the `components/char` equivalent instead (e.g. `@/components/char/button`, not `@/components/ui/button`). This keeps screens decoupled from the shadcn/base-ui primitives so the underlying primitive can change without touching every screen.
- Only create a new `components/char/*` component when it needs its own API, variant set, or visual identity beyond what the primitive exposes — don't create one just to re-export the primitive unchanged (though a thin re-export is fine when the goal is decoupling screens from `components/ui`, see `components/char/card.tsx`).
- `components/char/*` components expose a simple, semantic API (e.g. `variant="primary"`) — never raw style props (colors, hover colors, etc.). Variants are implemented internally using the design tokens.
- `Button` has two translucent variants (token colour at 15% fill / 40% border / full-colour text): `magenta` (`--char-magenta`) is used for "create" actions — the combobox "+" button, "+ Agregar variantes" and "+ Nuevo color/talle" — and `vivid` (blue, `info` token) is kept available; `ghost-danger` is the red icon button for row deletes. `primary` stays teal for the main action.
- `components/forms/*` components own the react-hook-form wiring (`useController`/`useFormContext`) and stay separate from `components/char` (which must stay agnostic of any form library).
- Never hardcode colors (hex/oklch/`bg-[#...]`) on a screen or component — use a Tailwind utility backed by a token (`bg-primary`, `text-danger`, `rounded-card`, ...) from `src/styles/tokens.css`. To change the palette, edit `tokens.css` (and its Tailwind bridge in `index.css`) only.

### Estética (identidad visual)

Boutique premium sobre la paleta de marca (crema + slate + acento teal + dorado `--char-brand-gold`): tipografía única **Inter** (`@fontsource-variable/inter`; `--font-sans` y `--font-display` apuntan a ella, `h1`–`h3` van en negrita en `index.css`; Geist y Lora se retiraron), sombras suaves en capas (`--shadow-card`, `--shadow-card-hover`, `--shadow-dropdown`) y easing `--ease-standard`. Motivos recurrentes: filo dorado superior que se extiende al hover (accesos del `DashboardPage` y `EntityCard`, vía `group-hover/card`), entrada suave con la utilidad `animate-rise` (`index.css`; el `PageHeader` y los accesos del dashboard la usan) y sidebar con degradé slate e ítem activo con filo dorado. Las tablas (`DataTable`) siguen el mismo lenguaje: encabezado slate (degradé del sidebar) con mayúsculas y filo dorado inferior, y fila en hover con degradé de acento que se despliega de izquierda a derecha (se desvanece) más barra lateral `--primary`. Las animaciones son solo CSS y `index.css` las apaga con `prefers-reduced-motion`; no agregues librerías de animación ni animaciones que remonten rutas.

### Routing

Routing is centralized in `src/app.router.tsx` using `react-router`'s `createBrowserRouter`, with two top-level route trees:

- `/admin/*` → `CharAdminLayout`, containing `DashboardPage` (index), `ClientsPage` and `UsersPage` (all behind `ProtectedRoute`)
- `/auth/*` → `AuthLayout`, containing `LoginPage` (behind `PublicRoute`)
- `/design-system` → `DesignSystemPage` (no layout), the Design System catalog described above

Every top-level route tree has `errorElement: <RouteErrorPage />` (`src/error/pages/`), shown when a screen throws or a lazy chunk fails to load.

Any unmatched route redirects to `/admin`. Route layouts (`AuthLayout`, `CharAdminLayout`) **and screens** (`LoginPage`, `DashboardPage`, `ProductsPage`, `ClientsPage`, `UsersPage`, `DesignSystemPage`) are lazy-loaded via `src/app.lazy.tsx` (`React.lazy`; screens keep their named export and are re-exported as `default` there). Both layouts wrap their `Outlet` in a `<Suspense>` (admin: `fallback={<PageSkeleton />}`) so navigating between screens doesn't unmount the frame, and `src/main.tsx` wraps the app in a top-level `<Suspense>`. When adding a new layout, register its lazy import in `app.lazy.tsx` rather than importing it directly in the router.

`src/CharApp.tsx` just renders `<RouterProvider router={appRouter} />` and is mounted from `src/main.tsx`.

### UI / styling

- Tailwind CSS v4 (via `@tailwindcss/vite`, config lives in `src/index.css` + `src/styles/tokens.css`, no `tailwind.config.js`)
- shadcn/ui, configured via `components.json`: style `base-nova`, base color `neutral`, icon library `lucide-react`, no RSC. Aliases: `@/components`, `@/components/ui`, `@/lib`, `@/hooks`.
- Component variants use `class-variance-authority` (`cva`); merge classes with the `cn()` helper from `@/lib/utils`, never string-concat Tailwind classes.
- `@base-ui/react` provides unstyled primitives that shadcn components wrap (see `src/components/ui/button.tsx` for the pattern: primitive + `cva` variants + `cn`).
- Path alias `@/*` → `src/*` is defined in both `tsconfig.app.json` and `vite.config.ts` — keep them in sync if changed.
- The React Compiler (babel plugin, via `@rolldown/plugin-babel`) is enabled in `vite.config.ts` — avoid manual `useMemo`/`useCallback` micro-optimizations that fight the compiler.

Some comments in the codebase (e.g. layout files) are written in Spanish; match existing conventions for consistency.

### Data fetching

- **Axios** for HTTP requests and **TanStack Query** (`@tanstack/react-query`) for server-state management: fetching, caching, mutations, and data synchronization. Do not reimplement these responsibilities manually with `fetch`, `useEffect`, or ad-hoc state when TanStack Query can handle it.

### Auth / session

`src/auth/store/auth.store.ts` (Zustand, persisted in `localStorage` as `auth-storage`) holds `access`/`refresh` tokens and the current user. `logout()` is async: it calls `POST /auth/logout/` (blacklists the refresh token, best-effort) and then clears the local session; `clearSession()` only clears the local session and is what the axios interceptor uses when the refresh fails. `src/lib/charApi.ts` is the shared axios instance: it attaches the `access` token and, on a 401 (except from `/auth/token/` and `/auth/token/refresh/`), refreshes once via `/auth/token/refresh/` and retries. The backend rotates and blacklists the refresh token on every refresh, so the new `refresh` returned must always be stored too (`setTokens(access, refresh)`) — saving only `access` logs the user out on the second renewal. The persisted session is validated once per page load: `ProtectedRoute` calls `verifySession()` (`GET /users/me/`) while `sessionVerified` (not persisted) is `false` and shows `AdminLayoutSkeleton` (a skeleton of the whole frame); a rejected session is cleared, an offline one is kept.

`src/lib/queryClient.ts` holds the shared `QueryClient`: no retries on 4xx (only network/5xx, max 2) and `staleTime` of 30 s.

### Permissions

Access control has a single mechanism (`src/auth/lib/permissions.ts`): `can(permission)` is true if `user.is_superuser` **or** `user.permissions` (from `GET /users/me/`, stored in `useAuthStore`) includes it. Never decide by role/group name (`group_names`/`groups` are informational) and never repeat the superuser logic in a component. Use `useCan()` in components (reactive), `<Can permission>` (`auth/components/Can.tsx`) to show/hide buttons and sections, and `RequirePermission` (`auth/components/RequirePermission.tsx`) on routes: without the module's "view" permission it shows a "Usted no posee permisos" alert and redirects to `/admin`. Permission strings live in `PERMISSIONS` (products module: `PERMISSIONS.products.<category|brand|productModel|color|size|product|productVariant|productImage>.<view|add|change|delete>` plus `PERMISSIONS.products.costPrice`). `adminNavItems` declare a `permission` and the sidebar, `AdminSearch` and the Dashboard only list modules the user can view (no permissions at all → the Dashboard shows the "sin permisos" message). `useGroups` only calls `/groups/` with `auth.view_group` (the groups selector in `UserFormDialog` is hidden otherwise; non-superusers can only assign groups they have, `useCanAssignGroup`). Nobody can deactivate themselves (`UserCard`). Permissions are re-requested (`refreshUser`) on reload, when the tab becomes visible (`ProtectedRoute`) and on any 403 (`charApi` interceptor); the 403 from the backend is the source of truth (`toApiError` shows its message or "No tenés permiso para esta acción").

### Products module data layer

Catalogs (`categories`, `brands`, `product-models`, `colors`, `sizes`), products and variants have no screens yet; their API layer lives in `admin/actions/<resource>.action.ts` (list / `getAll…` / get by id / create per catalog; products: get, get with variants, create, patch, delete; variants: create, delete) and `admin/hooks/use<Resource>.tsx` (`useCategories(params, {enabled})` paginated with `keepPreviousData` so it works with and without `search`; `useAll<Resource>` for the full list; `useCreate<Resource>` returns the record exactly as the API returned it). Query keys are centralized in `admin/config/query-keys.ts` (one factory per resource; invalidate through `.all`): creating a catalog record invalidates that resource and `catalogLookupKeys`; product mutations invalidate `products`, `product-variants` (Catalog grid) and `categories` (`products_count`); variant mutations invalidate the product's `with-variants` and the grid. `admin/utils/getAllPages.ts` walks `next` with `page_size=100` and keeps the API's order (never re-sort catalogs in the front). Money is always a decimal **string**: `admin/utils/money.ts` (`parseMoney("90.000,00")` → `"90000.00"`, `formatMoney`) and `isHexColor`. Duplicate-name errors carry `ApiError.existing`.

### Autocomplete (combobox)

`components/char/tabs` (`Tabs`/`TabsList`/`TabsTrigger`/`TabsContent`, built on base-ui Tabs via `components/ui/tabs`) is the accessible tab set (arrows, `aria-selected`). `components/char/combobox` (`Combobox<T>`, built on base-ui's `Combobox` via `components/ui/combobox`) is the generic, form-agnostic autocomplete: controlled `value: T | null`, `options`, `getOptionLabel`/`getOptionKey`/`getOptionGroup`, optional `onCreate` (shows the "+" button and the "Crear «…»" row), `loading`, `error`, `emptyMessage`. Passing `onInputChange` switches it to **remote mode** (parent searches and passes `options`; no local filtering); without it, it filters locally. Typing over a chosen value calls `onChange(null)`. Pure helpers (`splitByMatch`, `filterByLabel`, `groupOptions`) live in `highlight-match.ts`. `components/forms/FormCombobox` wires it to react-hook-form (the field value is the option, or whatever its `children` render-prop stores, e.g. the id). Ready-made, id-based configurations in `admin/components/`: `CategoryCombobox` (`?leaf=true`), `BrandCombobox`, `ProductModelCombobox` (`brandId` filters; without it labels are "Marca · Modelo"); all accept `initialOption` (an already-known option shown without fetching); they debounce 250 ms (`useComboboxSearch`), resolve a lone id with `GET /{resource}/:id/`, and only show "+"/"Crear…" with `onCreate` **and** the `add_` permission.

### Catalog create dialogs (brand, color, category, model, size)

`admin/components/BrandCreateDialog` and `ColorCreateDialog` (props `open`, `onOpenChange`, `onCreated(record)`, `initialName`) are the "Nueva marca / Nuevo color" modals opened from the combobox "+" / "Crear…" (one modal level: never open one over another). Both are built on `CatalogCreateDialog` (Dialog + form + "Cancelar"/"Crear y seleccionar" footer, discard confirmation with `AlertDialog` when dirty, general errors in an `AlertDialog`) and `useCatalogCreateFlow` (maps 400s onto fields; a duplicate-name 400 with `ApiError.existing` shows "Usar «Nike»", which fetches that record by id and hands it to `onCreated` without creating). `onCreated` always receives the record as the API returned it (normalized name/hex). The color tone is `ColorToneField` (native `<input type="color">` + text code + suggested tones + "Quitar tono"); it starts **empty ("sin tono")** and `hex` is only sent when a tone was chosen (`buildCreateColorRequest` in `admin/utils/colorTone.ts`, which also holds `TONE_SUGGESTIONS` and `isValidToneInput`). Stories mock the API through `catalogDialogStoryMocks.tsx` (Storybook only).

`CategoryCreateDialog` ("Nueva categoría": name + optional main category select built from `?root=true`, main categories with `products_count > 0` disabled "(ya tiene productos)", preview via `buildCategoryLabel` in `admin/utils/categoryLabel.ts`; a `parent` error is shown in the select and refetches the roots), `ProductModelCreateDialog` ("Nuevo modelo": `brandId` prop preloads the brand, otherwise `BrandCombobox` **without** "+"; `onCreated(model, brand)` hands both over) and `SizeCreateDialog` ("Nuevo talle": name uppercased while typing via `FormInput`'s `transform`, order suggested as max order + 10 and a "Así queda la lista" preview, both pure helpers in `admin/utils/sizeOrder.ts`; not wired anywhere yet, it arrives with the variants step) follow the same pattern. `FormSelect` options accept `disabled`.

### Products screens

`/admin/products` (nav "Productos", `products.view_product`) is the products listing (see "Products listing" below); `/admin/products/new` (`products.add_product`) is `admin/pages/products/ProductNewPage.tsx` and `/admin/products/:id` is `ProductEditPage` (see "Product edit screen" below). Routes are nested under a `products` route whose crumbs come from `navCrumb` + per-route static crumbs. The new-product form: schema, defaults, field list and `buildCreateProductRequest` in `admin/utils/productForm.ts` (cost only sent with `products.view_cost_price`; slug sent only if typed, lowercased; money via `parseMoney`; never `is_published`); promotion rules and the "Precio vigente" preview are pure functions in `admin/utils/productPromo.ts` (`validatePromotion`, `describeCurrentPrice`), `compareMoney` lives in `money.ts`, `slugify` is only the slug hint. Money fields use `components/forms/FormMoneyInput` (text, `inputmode="decimal"`, reformats on blur, field value is the typed text); `FormInput` accepts `prefix` (visual) and `transform`. Unsaved-changes confirmation uses `useBlocker` (+ `beforeunload`); after a successful save the redirect runs in an effect declared **after** `useBlocker`. The three form cards (Datos, Clasificación, Precios + promotion) and the create modals live in `admin/components/ProductFormFields` (shared by the new and edit screens; `readOnly` disables everything). Brand/model are kept consistent there (picking a model fills its brand; picking another brand clears a model that is not from it; clearing the brand keeps the model); only one create modal is open at a time.

### Products listing

`/admin/products` (`ProductsPage`, needs `products.view_product` **and** `products.view_productvariant`, nested `RequirePermission`) is the only merchandise screen (the old "Catálogo" was merged: no nav item, `/admin/catalog` redirects here). Header with "Nuevo producto" and a `components/char/tabs` view switch stored in the URL (`?view=products`; `variants` is the default and not written; switching view drops the other view's search/filters/ordering/page):

- **Variantes** (`ProductVariantsList`): one row per variant, `GET /product-variants/`, `useCatalogSearchParams`, `ProductVariantsTable` / `ProductVariantsCardList`. The product name / "Ver producto" go to `/admin/products/:id`. Never shows products without variants.
- **Productos** (`ProductsList`): one row per product, `GET /products/` (`getProductsAction`, `useProductList`, `useProductsSearchParams`; filters category, brand, model, is_published, `has_variants`, on_promo, min/max price; orderings `name`, `sale_price`, `effective_price`, `created_at`, `variants_count`). The API returns `variants_count` (always) and `variants` (only with `view_productvariant`); types `Product.variants_count`, `ProductListItem`. `ProductsTable` / `ProductsCardList` + `ProductCard`, `ProductVariantsSummary` (count, colors with their sizes, "Sin variantes" warning chip; helpers in `admin/utils/productList.ts`), `ProductStatusBadge`, row menu `useProductMenuItems` (Editar/Ver detalle, "Ver variantes" → `/admin/products/:id?tab=variants`, Eliminar via `ProductDeleteDialog`). This is where products without variants are found ("Sin variantes" filter). Cost is never shown.

### Product edit screen

`ProductEditPage` (the tab lives in the URL: `?tab=variants` / `?tab=images[&color=<id>]`; see "Product images") loads `GET /products/:id/` (`useProduct`) and, with `products.view_productvariant`, `with-variants` (`useProductWithVariants(id, {enabled})`; without the permission the "Variantes" tab is hidden). States: `ProductEditSkeleton`, error with "Reintentar", 404 "Producto no encontrado". The product name is the last breadcrumb via `useBreadcrumbLabel` (`admin/store/breadcrumb.store.ts`, read by `AdminBreadcrumb`). `ProductEditView` holds the form (same `ProductFormFields`, preloaded with `productToFormValues`; comboboxes get `initialOption` built by `productInitialOptions` so labels need no request) and the `components/char/tabs` ("Datos y precios" kept mounted, "Variantes (n)" via `ProductVariantsSection`, see below). `PATCH` sends only changed fields: `buildUpdateProductRequest` in `admin/utils/productEdit.ts` (promo = the three fields together or all `null`; empty slug = regenerate (`slug: ""`), only when unpublished; cost only with `products.view_cost_price`); after saving the form is `reset` with the API response. "Quitar promoción" / "Regenerar desde el nombre" only edit the form (applied on save). Sidebar cards: `ProductPublicationCard` (switch → `PATCH {is_published}`, disabled without `change_product` or, to publish, with no variants; shows the backend's `is_published` error), `ProductCurrentPriceCard` (API `current_price`/`is_on_promo`, `describeApiCurrentPrice`) and `ProductSummaryCard` (`summarizeVariants`). `ProductDeleteDialog` uses `AlertDialog` with `closeOnConfirm={false}` so a backend error stays inside the dialog; `useDeleteProduct` marks products stale without refetching (avoids a 404 flash). Without `change_product` the form is read-only.

`ProductVariantsSection` (Variantes tab) = header with "Agregar variantes" (`add_productvariant`, disabled while the panel is open), a `Notice` when the product is published, the in-page `ProductVariantsPanel` (not a modal) and the table with a per-row delete (`delete_productvariant`, `aria-label="Eliminar variante CHAR-0001"`). The panel: radio-group of colors (`useAllColors`), checkboxes of sizes grouped Letras/Números (`groupSizes`), "+ Nuevo color/talle" (`ColorCreateDialog`/`SizeCreateDialog`, one modal at a time, only with `add_color`/`add_size`; the new record ends up selected) and a preview from `buildVariantPreview` (new vs "Ya existe · se omite"; existing ones are never sent). Creation = `createVariantsSequentially` (one `POST /product-variants/` at a time, in order, so SKUs are consecutive; never throws, keeps going after a failure and returns one result per combination); on partial failure the panel stays open with a summary and "Crear" retries only the pending ones. All pure helpers live in `admin/utils/variantPlan.ts`. Without `view_color`/`view_size` the panel says so. `ProductVariantDeleteDialog` (opened from the table) keeps the backend's 400 message inside the dialog with a "Despublicar producto" shortcut, then retry. `CatalogCreateDialog` stops its `<form>` submit from bubbling (its React tree sits inside the screen's `<form>`; without it creating a catalog record also saved the product). `components/char/notice` (`Notice`: info/success/warning/danger inline strip) is the inline-notice resource. Stories mock the API with `ApiMockProvider` (`catalogDialogStoryMocks.tsx`).

### Product images (Imágenes tab)

Photos belong to a **product + color** (all sizes of a color share them). Third tab "Imágenes (n)" of `ProductEditPage` (needs `view_productvariant` **and** `view_productimage`, since the photos come from `GET /products/:id/with-variants/` → `images`; it is `keepMounted` so uploads in progress survive tab changes; the tab/`color` live in the URL and `goToImages(colorId)` pushes `?tab=images&color=<id>`). Sidebar there: Publicación (switch enabled only if published or `canPublish`), `ProductImagesSummaryCard`, `ProductImagesHelpCard` (`ProductImagesSideCards.tsx`).

- Layers: `actions/product-images.action.ts` (`uploadProductImageAction` = `FormData`, no manual `Content-Type`, progress + `AbortSignal`, throws the raw axios error; `update…`/`delete…` throw `ApiError`), `hooks/useProductImages.tsx` (`useSetPrimaryImage` / `useReorderImages` optimistic with rollback, `useSaveProductImage`, `useDeleteProductImage`; all refresh `with-variants` + the variants grid via `refreshProductImages`), `hooks/useImageUploadQueue.ts` (queue, 3 in parallel, per-file `queued → uploading → done | error`, cancel/retry/discard, 503 clears the queue and sets `storageUnavailable`, one toast per batch).
- **All pure logic is in `admin/utils/productImages.ts`** (no test runner, so keep it isolated): `validateImageFile`/`splitValidFiles`, `sortGalleryImages` (primary first, `sort_order`, `id`), `buildColorSections` (variant colors + colors with photos + local extras), `effectiveImage`, `reorderImages`/`moveImage`/`canMoveImage` (renumber 0..n-1 of one color, minimal `PATCH` set), `planImageUpdate` (detail panel → one `PATCH` of what changed; changing color sends `color`, `is_primary:false`, `sort_order` at the end of the destination), `planUploadBatch` (explicit `sort_order = max + 1 + index`; first file primary only if the color has no primary), `canPublish`/`wouldBreakPublication` (backend rule: publishing needs ≥1 active variant whose color has a photo; a published product can't lose its last variant-with-photo — delete that photo/variant or move its color — so those actions are disabled with help and a "Despublicar producto" shortcut, and a backend 400 shows its message with the same shortcut), `createConcurrencyQueue`, `classifyUploadError` (400/502/503/cancel), `getHttpStatus`.
- Components (`admin/components/`): `ProductImagesTab` (sections, "Fotos de otro color" = local empty section only, live region), `ColorImageGallery` (+ file input and drop zone, drag-and-drop reorder as an extra; arrows always available), `ImageTile`, `ImageUploadTile`, `ProductImageDetailPanel` (uses the `Dialog` — there is no side panel in the design system; **one modal level**: delete confirmation / failure / discard replace the panel content), `ColorPhotoThumb` ("Foto" column of the Variantes table; "Sin foto" navigates to the Images tab). `ProductVariantsSection` takes `images` + `onGoToImages` (column, one `Notice` per color without photos), `ProductVariantsPanel` takes `onViewImages` (toast action "Cargar fotos de {color}"), `ProductSummaryCard` takes `imagesSummary`. The new-product page has the locked "Imágenes" card. Story data: `productImageStoryData.ts`.

### Listings

Paginated listings (DRF `PageNumberPagination`, typed with `admin/interfaces/paginated.interface.ts` → `Paginated<T>`) keep `page`/`pageSize` in the screen state, pass them to the action and the `queryKey`, use `placeholderData: keepPreviousData` and go back to page 1 when the search, a filter or the page size changes (keep the page together with the criteria it was chosen for, as `UsersPage` does, so no request is sent with stale criteria). Render `components/char/pagination` below the list and cover the states with `components/char/state-message` (`error` with "Reintentar" / `empty`) and a skeleton (`components/char/skeleton`; e.g. `UsersListSkeleton`) for loading — prefer skeletons over spinners/"Cargando…" texts; dim the list while `isPlaceholderData`. See `admin/pages/users/UsersPage.tsx`. Searching is always `components/char/search-bar` (search field only) with the filters passed as `actions={<FiltersPopover … />}` (`components/char/filters-popover`, config-driven: chips, select, multiselect, text, date, checkbox; `multiselect` stores its options comma-separated, see `parseMultiValue`/`joinMultiValue`). `SearchBar` no longer has a collapsible "Más filtros" section — don't build filters by hand inside it.

Tabular listings use `components/char/data-table` (`DataTable`: sortable headers via DRF `ordering`, skeleton rows via `loading`, horizontal scroll under `--table-min-width`) instead of cards. `admin/pages/clients/ClientsPage.tsx` is the reference: on phones (below `md`) it shows cards (`ClientsCardList` → `ClientCard`, built on `EntityCard`, with an "Ordenar por" select + direction button since cards have no sortable headers) instead of the table — both are rendered and CSS (`max-md:hidden` / `md:hidden`) picks one; the row menu is shared via `useClientMenuItems`. It keeps search, filters, ordering, `page` and `page_size` **in the URL** (`admin/hooks/useClientsSearchParams.ts`, valid values only, defaults omitted) so the screen can be shared/reloaded; any criteria change goes back to page 1. Soft-deleted rows disappear from the cache immediately (`useDeleteClient`) and the toast offers "Deshacer" (`POST /clients/:id/restore/`, `clients.change_client`). `toApiError` turns a 429 into "Hiciste demasiadas solicitudes seguidas…".

Admin navigation lives in `src/admin/config/admin-nav.ts` (single source for the sidebar and the header search `AdminSearch`). `CharAdminLayout` renders `AdminBreadcrumb` (`components/char/breadcrumb`, `Breadcrumb` with `items: { label, to? }`) above the `Outlet`. Breadcrumbs are declared **per route** in `app.router.tsx` via `handle: { crumb } satisfies AdminRouteHandle` (`admin/config/route-handle.ts`) and collected with `useMatches()`: the layout route contributes "Inicio", each module uses `navCrumb("/admin/...")` (label taken from `adminNavItems`), and nested/dynamic routes add their own `crumb(loaderData)` (e.g. `/admin/clients/:id`). With a single crumb (Dashboard) nothing is shown. Never derive crumbs from the pathname. Toasts (`toast` from `@/components/char/sonner`) are tinted per type (`success`/`warning`/`error`/`info`) with the role tokens.

### Conventions

- Every component must have a JSDoc comment above its definition, and that JSDoc must be kept up to date whenever the component's props or behavior change.
- Storybook is installed (`.storybook/main.ts`) and used to describe/document component behavior. Config: `@storybook/react-vite` framework, addons `@chromatic-com/storybook`, `@storybook/addon-a11y`, `@storybook/addon-docs`. Stories are picked up from `src/**/*.stories.@(js|jsx|mjs|ts|tsx)` and `src/**/*.mdx` — colocate a `*.stories.tsx` next to any component that needs one. No example stories are left in the repo (the default `src/stories/` scaffold was removed). The vitest/playwright interaction-testing addon and `@storybook/addon-mcp` were deliberately left out — both pull in vitest/Playwright/Chromium as (transitive/peer) deps, which isn't needed just to document behavior.
- Respond to the user in Spanish when working in this repository.
- After creating or modifying files, always run Prettier and ESLint on them: `npx prettier --write <files>` then `npx eslint --fix <files>`, and make sure `npx eslint <files>` is clean. A `PostToolUse` hook in `.claude/settings.json` already does this automatically for files written with the Write/Edit tools; files changed through Bash (scripts, `sed`, heredocs) are not covered, so run both commands manually after those. Order matters: Prettier first, then ESLint's `--fix`. `eslint.config.js` allows a single blank line between statements (`no-multiple-empty-lines` with `max: 1`, same as Prettier's output) but not blank lines at the start/end of a file or block (`padded-blocks: never`).
- Whenever code changes, update the affected JSDoc comments, the READMEs and the `CLAUDE.md` files in the same change if they describe it.
